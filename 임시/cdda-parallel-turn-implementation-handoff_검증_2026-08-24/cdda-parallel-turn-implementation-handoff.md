# Cataclysm-DDA 자동 세계 갱신 병렬화 구현 인계

## 1. 이 문서의 독자와 목적

이 문서는 이전 대화를 볼 수 없는 새 Codex 세션을 위한 작업 지시서다.

새 세션은 C++17, Git, PowerShell, 단위 테스트의 일반 사용법만 안다고 전제한다. 새 세션이 이전 대화의 용어와 결정을 안다고 전제하지 않는다.

새 세션은 이 문서의 3절부터 12절까지 설명한 설계를 구현한다. 구현 대상은 `C:\cdda\cataclysm-dda`의 게임 소스다.

구현 목표는 플레이어가 행동한 뒤 게임 세계를 한 번 갱신하는 데 걸리는 실제 시간을 줄이는 것이다. 구현은 여러 중앙 처리 장치(CPU) 코어를 사용한다.

그래픽 처리 장치(GPU)는 첫 완료 범위에 없다. CPU 구현을 측정한 뒤 조밀한 격자 계산에만 GPU를 검토한다.

## 2. 프로젝트와 현재 턴 처리

Cataclysm-DDA는 격자 지도를 사용하는 싱글 플레이어 생존 게임이다. 이 문서에서 `게임 상태`는 한 시점의 지형, 아이템, 생물, 플레이어, 차량, 날씨, 필드, 소리를 모두 뜻한다.

`타일`은 격자 지도의 한 칸이다. 지형, 가구, 함정, 방사선, 아이템, 필드가 타일에 연결된다.

`필드`는 타일에 존재하는 불, 연기, 가스, 산과 같은 시간 변화 효과다. `활성 아이템`은 매 턴 시간 변화나 사용 효과를 계산해야 하는 아이템이다.

`냄새 배열`은 각 타일의 냄새 세기를 저장하는 격자다. `가시성 캐시`는 생물과 플레이어가 볼 수 있는 타일을 빠르게 찾도록 미리 계산한 자료다.

`필드 방출`은 지형이나 가구가 새 필드를 만드는 규칙이다. `비플레이어 캐릭터`는 사람이 조작하지 않고 게임 인공지능이 행동시키는 인간형 생물이다.

게임은 `src/do_turn.cpp`의 `game::do_turn()`으로 한 게임 턴을 처리한다. `game::do_turn()`은 플레이어 입력과 자동 세계 갱신으로 구성된다.

플레이어 입력은 플레이어가 이동, 공격, 활동을 선택하는 구간이다. 자동 세계 갱신은 플레이어 입력 뒤에 게임 규칙이 세계를 바꾸는 구간이다.

현재 `game::do_turn()`은 자동 세계 갱신을 정해진 순서로 실행한다. 주요 순서는 다음과 같다.

```text
냄새 확산
바닥과 낙하 처리
차량 이동
필드 처리
활성 아이템 처리
폭발 처리
생물의 필드 효과 처리
소리 처리
가시성 캐시 계산
몬스터와 비플레이어 캐릭터 행동
지형과 가구의 필드 방출
플레이어 상태 갱신
날씨와 음향 효과 처리
```

현재 함수들은 하나의 가변 게임 상태를 즉시 바꾼다. 뒤에서 실행하는 함수는 앞 함수가 같은 턴에 만든 변경을 볼 수 있다.

예를 들어 `src/map_field.cpp`의 불 필드는 아이템을 태우고 차량을 손상시킨다. 불 필드는 지형과 가구도 바꿀 수 있다.

`src/monmove.cpp`의 생물 이동은 앞 생물의 이동 결과를 뒤 생물이 보게 한다. 앞 생물이 비운 타일에는 뒤 생물이 같은 턴에 들어갈 수 있다.

이 즉시 변경 방식은 현재 실행 순서에 결과를 결합한다. 여러 스레드가 현재 함수를 그대로 호출하면 데이터 경쟁과 순서 변화가 발생한다.

## 3. 사용자가 선택한 새 턴 규칙

사용자는 자동 세계 갱신 안에서 생긴 변경을 다른 계산이 같은 갱신 안에 보지 않아도 된다고 결정했다. 모든 병렬 계산은 자동 세계 갱신을 시작할 때 고정한 같은 게임 상태를 읽는다.

병렬 계산이 만든 변경은 모두 계산이 끝난 뒤 적용한다. 적용이 끝난 게임 상태는 다음 자동 세계 갱신의 입력이 된다.

두 계산이 같은 타일이나 같은 객체를 바꾸면 현재 `game::do_turn()`의 시스템 순서로 변경을 적용한다. 같은 시스템 안에서는 현재 소스 순회 순서로 변경을 적용한다.

이 규칙은 현재 직렬 엔진과 완전히 같은 턴 결과를 요구하지 않는다. 현재 직렬 엔진은 같은 턴의 앞 변경을 뒤 계산이 보기 때문이다.

`난수 초기값(seed)`은 난수 열의 시작 값을 정하는 입력이다. `작업자 스레드`는 병렬 계산을 나눠 실행하는 스레드다.

새 규칙은 다음 조건을 요구한다.

- 같은 시작 게임 상태와 같은 난수 초기값은 같은 끝 게임 상태를 만든다.
- 작업자 스레드 수가 달라도 같은 끝 게임 상태를 만든다.
- 작업자 실행 순서가 달라도 같은 끝 게임 상태를 만든다.
- 각 계산은 현재 게임 규칙을 자기 입력 상태에 적용한다.
- 같은 대상을 향한 변경은 현재 시스템 순서로 적용한다.

사용자는 이 의미 변화를 승인했다. 새 세션은 현재 직렬 엔진의 타일 순회 효과를 복원하려고 병렬 계산을 다시 직렬화하지 않는다.

## 4. 구현 용어

이 절은 이후 절에서 사용하는 구현 용어를 정의한다.

### 4.1 상태와 계산

`턴 입력 상태`는 자동 세계 갱신을 시작할 때 고정한 게임 상태다. 코드 이름은 `turn_input_state`다.

`턴 입력 상태`는 읽기 전용이다. 자동 세계 갱신이 끝날 때까지 어떤 스레드도 `턴 입력 상태`를 바꾸지 않는다.

`평가 작업`은 `턴 입력 상태`를 읽고 계산 결과를 만드는 함수 호출 하나다. 코드 이름은 `turn_job`이다.

`작업 소유 대상`은 평가 작업 하나가 직접 갱신할 수 있는 객체나 배열 구역이다. 생물 하나와 냄새 배열의 행 구역이 작업 소유 대상의 예다.

`다음 게임 상태`는 평가 작업의 결과를 모두 적용한 게임 상태다. 다음 자동 세계 갱신은 `다음 게임 상태`를 새 `턴 입력 상태`로 사용한다.

`다음 상태 버퍼`는 `다음 게임 상태`의 값을 기록하는 메모리다. 평가 작업은 `턴 입력 상태`와 다음 상태 버퍼를 구분한다.

### 4.2 결과와 충돌

`소유 결과`는 평가 작업이 자기 작업 소유 대상에 만든 결과다. 평가 작업은 소유 결과를 전용 다음 상태 버퍼에 직접 쓴다.

`외부 변경`은 평가 작업이 다른 작업 소유 대상을 바꾸려는 결과다. 공격 대상의 체력 감소와 이웃 타일의 필드 증가는 외부 변경이다.

`변경 레코드`는 외부 변경을 값으로 표현한 구조체다. 코드 이름은 `turn_change`다.

`순서 키`는 같은 대상을 향한 변경 레코드의 적용 순서를 나타낸다. 코드 이름은 `turn_change_order`다.

`병합기`는 변경 레코드를 대상별로 모으고 순서 키대로 적용한다. 코드 이름은 `turn_change_reducer`다.

### 4.3 실행 방식

`턴 작업 실행기`는 평가 작업을 작업자 스레드에 배정하고 완료를 기다리는 객체다. 코드 이름은 `turn_executor`다.

`직렬 실행 모드`는 턴 작업 실행기가 작업자 하나로 모든 평가 작업을 실행하는 모드다.

`병렬 실행 모드`는 턴 작업 실행기가 작업자 여러 명으로 평가 작업을 실행하는 모드다.

`상태 검증값`은 게임 상태의 의미 있는 값을 정해진 순서로 직렬화한 뒤 계산한 고정 길이 숫자다. 포인터 주소와 메모리 할당 주소는 상태 검증값에 포함하지 않는다.

### 4.4 고위험 용어 사전

| 용어 | 뜻 | 옳은 예 | 그르게 읽으면 안 되는 예 |
|---|---|---|---|
| 턴 입력 상태 | 자동 세계 갱신이 읽는 고정 게임 상태 | 모든 생물 작업이 같은 점유 상태를 읽는다 | 작업이 다른 작업의 새 위치를 읽는다 |
| 같은 결과 | 상태 검증값이 같은 결과 | 작업자 수 1과 4의 상태 검증값이 같다 | 현재 직렬 엔진과 난수 호출 순서까지 같다 |
| 현재 시스템 순서 | `game::do_turn()`이 시스템을 호출하는 순서 | 필드 변경 뒤에 아이템 변경을 적용한다 | 필드 변경을 본 뒤 아이템 계산을 다시 실행한다 |
| 직접 쓰기 | 작성자가 하나인 다음 버퍼 위치에 쓰기 | 생물 작업이 자기 생물의 다음 상태를 쓴다 | 두 생물 작업이 같은 생물을 동시에 쓴다 |

## 5. 성능 측정 방법과 기준 자료

현재 작업 트리에는 Windows용 턴 프로파일러가 있다. 프로파일러는 `game::do_turn()` 안의 이름 붙은 코드 구간이 사용한 CPU 사이클을 기록한다.

CPU 사이클은 CPU가 명령을 처리하며 진행한 횟수를 세는 단위다. CPU 사이클은 사용자가 기다린 실제 시간과 다른 측정값이다.

프로파일러는 JSON 구조화 텍스트에 원자료를 저장한다. 프로파일러는 웹 브라우저에서 보는 HTML 보고서도 저장한다.

이 문서에서 `측정 요소`는 프로파일러가 이름을 붙인 코드 구간이다. `creatures`와 `player.temperature`가 측정 요소의 예다.

`독점 CPU 사이클`은 측정 요소 자체에서 사용한 CPU 사이클이다. 측정 요소 안의 하위 측정 요소가 사용한 사이클은 제외한다.

`턴 지분`은 한 턴의 전체 CPU 사이클 중 측정 요소의 독점 CPU 사이클이 차지한 비율이다.

`평균 지분`은 10,000개 턴의 턴 지분을 산술 평균한 값이다. 프로파일 HTML은 이 값을 `Mean share`라고 표시한다.

`99백분위 지분`은 턴 지분을 작은 값부터 정렬했을 때 99% 위치의 값이다. 프로파일 HTML은 이 값을 `P99 share`라고 표시한다.

기준 자료는 아래 두 파일이다.

- `C:\cdda\cataclysm-dda\turn-profile-results\20260824-165814\turn-profile.json`
- `C:\cdda\cataclysm-dda\turn-profile-results\20260824-165814\turn-profile.html`

기준 실행은 10,000턴을 기록했다. 기준 실행의 난수 초기값 문자열은 `cdda-turn-profile-v1`이다.

기준 실행은 타일 그래픽과 소리를 켰다. 기준 실행은 자동 저장을 껐다. 기준 실행은 Microsoft Visual C++(MSVC) 194435215로 빌드했다.

프로파일 HTML의 Summary 행은 누적 독점 CPU 사이클로 정렬된다. Summary 행은 평균 지분 순서로 정렬되지 않는다.

프로파일 측정 요소의 이름과 실제 계산은 아래와 같다.

`background.other`는 주 스레드가 아닌 기존 백그라운드 작업의 CPU 사이클이다. 두 특수 측정 요소는 병렬 전환 대상에서 제외한다.

## 8. 자동 세계 갱신의 새 실행 순서

이 절은 게임 안의 시간 좌표를 정한다. `턴 입력 상태`는 소스 저장소의 현재 상태가 아니다.

`턴 입력 상태`는 플레이어가 이번 턴의 행동을 끝낸 뒤 게임 메모리에서 고정한 값이다. `턴 입력 상태`에는 플레이어 행동의 결과가 들어 있다.

최종 실행 순서는 아래와 같다.

```text
1. 기존 직렬 코드가 달력, 이벤트, 날씨, 플레이어 입력을 처리한다.
2. 기존 직렬 코드가 바닥, 차량, 대기 중인 폭발을 처리한다.
3. 게임이 턴 입력 상태 S_t를 고정한다.
4. 턴 작업 실행기가 13개 측정 요소의 평가 작업을 실행한다.
5. 병합기가 외부 변경을 대상별 순서대로 적용한다.
6. 게임이 다음 게임 상태 S_t+1을 공개한다.
7. 기존 직렬 코드가 화면, 사기, 종료 처리를 실행한다.
```

1단계는 `game::do_turn()`의 시작부터 `player.input` 구간의 끝까지다. `player.body`는 1단계에서 제거하고 4단계로 옮긴다.

2단계는 `vehicles.view`, `map.floor`, `map.vehicles`, 이미 대기 중인 `map.explosions`를 실행한다. 2단계가 끝난 직후 `턴 입력 상태`를 고정한다.

4단계의 필드나 아이템이 새 폭발을 만들면 `queue_explosion` 변경 레코드를 만든다. 새 폭발은 `다음 게임 상태`에 대기 상태로 저장한다.

새 폭발은 다음 자동 세계 갱신의 2단계에서 실행한다. 따라서 병렬 평가 중 만든 폭발은 현재 엔진보다 한 자동 세계 갱신 늦게 실행될 수 있다.

7단계는 `overmap.npcs`, `render`, `weather.effects`, `ui.progress`, `map.visibility_invalidate`, `player.morale`, `player.finalize`, `debug.capture`를 포함한다.

## 9. 공통 자료 구조와 실행 계약

### 9.1 턴 입력 상태

`turn_input_state`는 평가 작업이 읽는 값과 읽기 전용 보기를 제공한다. `turn_input_state`는 가변 `map`, `Creature`, `item`, `vehicle` 포인터를 공개하지 않는다.

`turn_input_state`는 아래 입력을 제공한다.

```text
게임 턴 번호와 난수 초기값
현재 날씨와 달력 값
지형, 가구, 함정, 방사선, 필드의 타일 배열
냄새 배열과 가시성 입력 배열
플레이어 시작 상태
몬스터와 비플레이어 캐릭터 시작 상태
차량과 차량 아이템의 읽기 전용 상태
지상 활성 아이템의 읽기 전용 상태
현재 소리 사건과 소리 위치 자료
field_cache와 submaps_with_active_items
필드 방출 위치 목록 두 개
평가 작업이 읽는 게임 옵션 값
```

전체 게임 상태를 턴마다 깊은 복사하지 않는다. 바뀌지 않는 데이터는 공유 읽기 전용 저장소를 참조한다.

바뀌는 조밀 배열은 현재 버퍼와 다음 버퍼 두 개를 사용한다. 자동 세계 갱신이 끝나면 두 버퍼의 역할을 교환한다.

희소 객체는 안정적인 객체 식별자로 참조한다. 안정적인 객체 식별자는 메모리 주소를 사용하지 않는다.

### 9.2 평가 작업

모든 평가 작업은 아래 논리 계약을 따른다.

```cpp
struct turn_job {
    turn_system system;
    turn_owner owner;

    void evaluate(
        const turn_input_state &input,
        turn_owned_output &owned_output,
        turn_change_buffer &external_changes
    ) const;
};
```

`turn_system`은 기존 측정 요소의 실행 순서를 나타내는 열거형이다. `turn_owner`는 작업 소유 대상을 식별한다.

`turn_owned_output`은 소유 결과를 기록하는 전용 다음 버퍼 보기다. 다른 평가 작업은 같은 위치를 받지 않는다.

`turn_change_buffer`는 외부 변경의 변경 레코드를 보관한다. 작업자마다 버퍼 하나를 미리 할당하고 턴 사이에 재사용한다.

### 9.3 변경 레코드

원본 대조에서 확인한 변경 레코드 종류는 아래와 같다.

```text
move_creature
damage_creature
apply_creature_effect
update_creature_visibility_memory
spawn_creature
despawn_creature
damage_vehicle_part
modify_vehicle_state
destroy_vehicle
modify_field
transform_terrain
transform_furniture
modify_radiation
modify_scent
invalidate_map_cache
move_item
modify_item
spawn_item
destroy_item
queue_explosion
queue_game_sound
audio_command
request_player_activity_cancel
game_message
queue_scripted_event
```

`queue_game_sound`는 생물 인공지능이 다음 자동 세계 갱신에서 듣는 게임 소리를 기록한다. `audio_command`는 사용자의 스피커로 재생할 음향 명령이다.

`queue_scripted_event`는 데이터로 정의한 게임 사건을 다음 실행 시점까지 대기시킨다. `invalidate_map_cache`는 타일 변경으로 낡은 캐시의 종류와 좌표를 기록한다.

`request_player_activity_cancel`은 플레이어 활동 중단 요청을 기록한다. `game_message`는 사용자에게 표시할 번역 가능한 메시지와 인자를 기록한다.

이 목록은 확인된 종류의 목록이다. 이 목록은 변경 레코드 종류의 상한이 아니다.

평가 작업으로 옮길 기존 함수마다 가변 객체 쓰기를 전수 검색한다. 기존 종류가 외부 변경 하나를 표현하지 못하면 열거형을 먼저 확장한다.

같은 코드 변경에 새 종류의 병합 테스트를 추가한다. 외부 변경을 버리거나 일반 콜백으로 감싸지 않는다.

변경 레코드는 일반 콜백과 `std::function`을 저장하지 않는다. 변경 레코드는 직렬화할 수 있는 식별자와 값만 저장한다.

### 9.4 변경 적용 순서

각 변경 레코드는 아래 순서 키를 가진다.

```cpp
struct turn_change_order {
    turn_system system;
    turn_source_kind source_kind;
    std::uint64_t source_order;
    std::uint32_t local_order;
};
```

`system`의 순서는 현재 `game::do_turn()`의 순서를 따른다.

```text
player.body
sounds.markers
scent
map.fields
map.items
map.creature_fields
sounds.ai
map.visibility
creatures
map.emissions
player.replenish
player.temperature
sounds.effects
```

타일 원본의 `source_order`는 `(z, submap_x, submap_y, tile_x, tile_y)`를 정수로 부호화한 값이다. 순서는 이 튜플의 사전식 순서다.

생물 원본의 `source_order`는 `turn_input_state`를 만들 때 기록한 현재 생물 순회 번호다. 몬스터 번호가 모든 비플레이어 캐릭터 번호보다 앞선다.

아이템 원본의 `source_order`는 `active_item_cache::get_for_processing()`이 반환한 배열의 인덱스다.

차량 아이템 원본의 `source_order`는 `(z, submap_x, submap_y, vehicle_index, part_index, item_index)` 순서다. 각 인덱스는 `turn_input_state`를 만들 때 현재 컨테이너 순서에서 기록한다.

필드 방출 원본의 `source_order`는 가구 방출 위치 목록 또는 지형 방출 위치 목록의 인덱스다. 가구 목록이 지형 목록보다 앞선다.

`local_order`는 평가 작업 하나가 변경 레코드를 만든 순서다. 각 평가 작업은 0부터 시작한다.

병합기는 대상 종류와 대상 식별자로 변경 레코드를 분할한다. 병합기는 대상 하나 안에서만 순서 키를 정렬한다.

병합기는 모든 변경 레코드를 한 전역 배열에서 정렬하지 않는다. 서로 다른 대상의 변경은 서로 다른 작업자가 병합할 수 있다.

같은 대상의 변경 레코드는 아래 규칙으로 적용한다.

| 충돌 | 적용 규칙 |
|---|---|
| 같은 목적지로 이동 | 순서 키가 작은 이동부터 현재 점유 배열에 적용한다 |
| 점유된 목적지로 이동 | 앞 이동이 목적지를 비웠으면 성공하고, 아니면 실패한다 |
| 생물 피해와 생물 효과 | 순서 키대로 적용하고, 생물이 죽으면 뒤 효과를 무시한다 |
| 생물 제거와 생물 수정 | 제거 뒤의 수정은 무시한다 |
| 차량 제거와 차량 수정 | 제거 뒤의 수정은 무시한다 |
| 같은 차량 부품의 피해 | 순서 키대로 피해를 적용한다 |
| 아이템 제거와 아이템 수정 | 제거 뒤의 수정은 무시한다 |
| 같은 지형 또는 가구 변환 | 순서 키대로 적용하므로 마지막 변환이 남는다 |
| 같은 종류의 필드 변경 | 순서 키대로 기존 필드 강도와 수명 규칙을 적용한다 |
| 여러 아이템 생성 | 순서 키 순서로 모두 삽입한다 |
| 여러 폭발 대기 | 순서 키 순서로 모두 대기열에 넣는다 |
| 여러 게임 소리 사건 | 순서 키 순서로 모두 게임 소리 대기열에 넣는다 |
| 여러 음향 명령 | 순서 키 순서로 오디오 소유 스레드에 보낸다 |
| 여러 사용자 메시지 | 순서 키 순서로 메시지 기록에 넣는다 |

실패한 이동은 생물의 시작 위치를 유지한다. 병합기는 실패한 이동을 같은 자동 세계 갱신에서 다시 계산하지 않는다.

### 9.5 난수

평가 작업은 `src/rng.cpp`의 전역 난수 엔진을 호출하지 않는다. 평가 작업은 새 `turn_random_stream`을 사용한다.

`turn_random_stream`은 아래 네 값을 입력으로 받는다.

```text
게임 턴 번호
turn_system 값
turn_owner 식별자
평가 작업 안의 난수 호출 번호
```

`turn_random_stream`은 명시한 정수 해시 알고리즘을 사용한다. `std::hash`는 사용하지 않는다.

테스트는 작업자 수 1, 2, 4에서 같은 난수 결과를 요구한다. 테스트는 평가 작업 제출 순서를 바꿔도 같은 난수 결과를 요구한다.

## 10. 계산 그룹별 구현

### 10.1 생물 계산 그룹

현재 `src/do_turn.cpp`의 `monmove()`는 몬스터를 하나씩 처리한 뒤 비플레이어 캐릭터를 처리한다. 최종 구현은 생물 하나마다 평가 작업 하나를 만든다.

생물 평가 작업은 아래 입력을 `turn_input_state`에서 읽는다.

```text
자기 생물 상태
주변 타일 상태
다른 생물의 시작 위치
시작 시점의 소리 상태
자기 타일의 시작 필드 상태
```

생물 평가 작업은 아래 소유 결과를 직접 쓴다.

```text
자기 상태 효과
자기 이동력
자기 행동 계획 결과
```

생물 평가 작업은 공격, 이동, 소환, 사망, 다른 생물 효과를 변경 레코드로 만든다.

여러 생물이 같은 목적지로 이동하면 병합기가 작은 `source_order`를 가진 이동을 선택한다. 선택되지 않은 생물은 시작 위치에 남는다.

선택되지 않은 생물은 같은 자동 세계 갱신에서 재계획하지 않는다. 다음 자동 세계 갱신에서 새 `turn_input_state`를 보고 다시 계획한다.

`sounds.markers`는 비플레이어 캐릭터마다 듣기 결과를 계산하는 평가 작업으로 옮긴다. 플레이어의 듣기 결과도 별도 평가 작업으로 계산한다.

`sounds.ai`는 시작 소리 사건에서 다음 게임 상태의 인공지능용 소리 자료를 만드는 평가 작업으로 옮긴다.

몬스터와 비플레이어 캐릭터의 필드 적용은 현재 `monmove()` 안의 동작을 생물 평가 작업으로 옮긴다. 이 계산의 CPU 사이클은 `creatures` 측정 요소에 포함되어 있다.

### 10.2 플레이어 상태 계산 그룹

플레이어 상태 계산은 같은 플레이어를 대상으로 하는 평가 작업 네 개다.

| 평가 작업 | 현재 함수 | 소유 결과 |
|---|---|---|
| player_body_job | `Character::update_body()` | 필요, 체력, 비타민, 수면 값 |
| player_replenish_job | `Character::process_turn()` | 이동력, 효과, 소지품 값 |
| player_temperature_job | `update_bodytemp()`, `update_body_wetness()`, `apply_wetness_morale()` | 신체 부위 온도, 젖음, 사기 변화 |
| player_field_job | `map::creature_in_field()`의 플레이어 호출 | 플레이어 필드 피해와 효과 |
| player_visibility_job | `game::mon_info_update()` | 적대 생물 표시, 안전 모드, 활동 중단 결과 |

다섯 평가 작업은 같은 플레이어 시작 상태를 읽는다. 다섯 평가 작업은 가변 플레이어 객체를 공유하지 않는다.

다섯 평가 작업은 각각 고정 형식 결과 구조체를 만든다. 구조체 이름은 아래 목록으로 닫는다.

```text
player_body_output
player_replenish_output
player_temperature_output
player_field_output
player_visibility_output
```

`player_visibility_job`은 보이는 생물마다 `update_creature_visibility_memory` 변경 레코드를 만들 수 있다. 이 레코드는 몬스터의 무시 거리와 마지막 확인 턴을 갱신한다.

`player_visibility_output`은 적대 생물 목록, 안전 모드, 활동 중단 요청, 플레이어 효과, 사용자 메시지를 담는다.

`player_visibility_job`의 기준 CPU 사이클은 `map.emissions` 측정 요소에 포함되어 있다. 6.2절의 27.7311%에는 이 CPU 사이클이 들어 있지 않다.

플레이어 병합기는 다섯 결과 구조체를 `turn_system` 순서로 적용한다. 플레이어 병합기는 작업자 실행 순서를 사용하지 않는다.

### 10.3 음향 계산 그룹

현재 `src/sounds.cpp`의 `sounds.effects` 구간은 청력 손실 종료, 위험 음악, 차량 음향, 낮은 체력 음향을 계산한다. 같은 함수들은 오디오 라이브러리도 호출한다.

새 음향 평가 작업은 게임 상태를 읽고 `audio_command` 변경 레코드만 만든다. 음향 평가 작업은 오디오 라이브러리를 호출하지 않는다.

플레이어가 귀가 들리지 않으면 `sounds.markers`의 듣기 평가 작업이 청력 손실 시작 명령을 만든다. 이 명령도 `audio_command` 변경 레코드다.

오디오 소유 스레드 하나가 `audio_command`를 순서대로 실행한다. 다른 작업자 스레드는 오디오 라이브러리를 호출하지 않는다.

오디오 소유 스레드는 다음 게임 상태 공개를 막지 않는다. 게임 종료는 오디오 명령 처리를 중단하고 오디오 소유 스레드를 합류시킨다.

### 10.4 지도 계산 그룹

`scent`와 `map.visibility`는 많은 인접 셀을 같은 규칙으로 계산한다. 두 계산은 조밀 배열 평가 작업으로 구현한다.

`scent`는 목적지 셀이 시작 냄새 배열의 이웃 값을 읽게 한다. 목적지 셀은 다음 냄새 배열의 자기 위치만 쓴다.

`가시성 패스`는 `map::build_map_cache()`가 가시성 자료 전체를 한 번 순회하는 계산 단계다. 현재 함수에는 서로의 결과를 요구하는 가시성 패스가 여러 개 있다.

`map.visibility`는 현재 가시성 패스 순서를 유지한다. 같은 가시성 패스 안의 z층이나 행 구역만 병렬로 계산한다.

서브맵은 12×12 타일 묶음이다. `field_cache`는 필드가 있는 서브맵을 표시한다.

`submaps_with_active_items`는 활성 아이템이 있는 서브맵의 좌표를 저장한다. 두 현재 목록은 희소 계산의 작업 위치를 제한한다.

`map.fields`는 `field_cache`가 표시한 서브맵마다 평가 작업 하나를 만든다. `map.items`는 `submaps_with_active_items`의 서브맵마다 평가 작업 하나를 만든다.

`map.items`는 차량 아이템도 처리한다. 차량 아이템은 차량이 들어 있는 서브맵마다 별도 평가 작업 하나를 만든다.

`map.emissions`의 필드 방출 부분은 가구 방출 위치 목록과 지형 방출 위치 목록을 입력으로 사용한다. 실행기는 각 목록을 작업자 수만큼 연속 구간으로 나눈다.

`map.emissions`의 `mon_info_update()` 부분은 `player_visibility_job`으로 옮긴다. 프로파일러는 두 부분의 CPU 사이클을 새 측정 요소로 분리한다.

필드, 활성 아이템, 방출 위치가 없는 타일에는 평가 작업을 만들지 않는다.

## 11. 명령 생성 비용을 제한하는 규칙

사용자는 변경 레코드를 만들고 적용하는 비용이 병렬화 이득을 없앨 수 있다고 우려했다. 구현은 아래 규칙으로 그 비용을 제한한다.

1. 평가 작업은 소유 결과를 변경 레코드로 만들지 않는다.
2. 평가 작업은 외부 변경만 변경 레코드로 만든다.
3. 작업자마다 변경 레코드 메모리를 미리 할당한다.
4. 작업자는 턴마다 변경 레코드 메모리를 새로 할당하지 않는다.
5. 병합기는 대상별 배열이나 버킷으로 변경 레코드를 분할한다.
6. 병합기는 전역 정렬을 하지 않는다.
7. 조밀 배열 계산은 다음 버퍼에 직접 쓴다.
8. 희소 계산은 현재 활성 목록을 유지한다.
9. 턴 작업 실행기는 작업자 스레드를 게임 시작 때 만든다.
10. 턴 작업 실행기는 게임 종료 때 작업자 스레드를 합류시킨다.

턴 작업 실행기는 턴마다 스레드를 만들지 않는다. 턴 입력 상태도 전체 게임 객체를 턴마다 깊은 복사하지 않는다.

`--turn-workers N`의 `N`은 주 스레드를 포함한 전체 평가 스레드 수다. `N=1`이면 새 작업자 스레드를 만들지 않는다.

`N=0`이면 `std::thread::hardware_concurrency()` 값을 사용한다. 함수가 0을 반환하면 전체 평가 스레드 수를 1로 정한다.

전체 평가 스레드 수가 `N`이면 턴 작업 실행기는 작업자 스레드를 `N-1`개 유지한다. 주 스레드는 남은 평가 작업을 실행한다.

## 12. CPU 실행과 GPU 후속 판단

첫 구현은 CPU 작업자 스레드만 사용한다. 이유는 생물과 플레이어 계산이 전체 평균 지분의 72.35%를 차지하기 때문이다.

생물과 플레이어 계산은 분기, 가변 목록, 객체 식별자를 많이 사용한다. 이 계산은 GPU 타일 커널보다 CPU 작업자에 더 적합하다.

GPU 후보는 `scent`와 `map.visibility` 두 계산뿐이다. 두 계산은 조밀 배열을 사용한다.

CPU 구현을 완료한 뒤 두 계산이 병렬 턴의 실제 완료 시간을 제한하면 GPU 프로토타입을 만든다. 두 계산이 완료 시간을 제한하지 않으면 GPU 프로토타입을 만들지 않는다.

GPU 구현은 같은 `turn_input_state`와 다음 버퍼 형식을 사용한다. GPU 구현은 다른 게임 규칙을 만들지 않는다.

### 16.2 프로파일러를 병렬 작업에 맞춘다

현재 프로파일러는 주 스레드 밖의 CPU 사이클을 `background.other`로 기록한다. 병렬 작업자 사이클을 이 값과 구분해야 한다.

`프로파일 형식 버전`은 JSON의 `schema_version` 값이다. 프로파일 필드의 뜻이 바뀌면 이 값을 올린다.

각 작업자 스레드는 평가 작업 시작과 끝에서 자기 스레드 CPU 사이클을 읽는다. 작업자 스레드는 차이를 자기 전용 누적 배열에 더한다.

평가 파동이 끝나면 주 스레드가 작업자별 누적 배열을 합친다. 프로파일러의 기존 열린 구간 스택을 작업자 스레드가 공유하지 않는다.

프로파일 JSON은 `worker.<측정 요소>`와 `reduce.<측정 요소>` 이름으로 새 값을 저장한다. 기존 `background.other`는 새 작업자 값을 뺀 나머지 백그라운드 사이클만 저장한다.

1. 프로파일 형식 버전을 올린다.
2. 생물 계산을 상태 갱신, 계획, 이동, 비플레이어 캐릭터 처리로 나눈다.
3. 플레이어 상태 계산 다섯 개에 하위 측정 구간을 추가한다.
4. 체온, 젖음, 젖음 사기 계산을 서로 구분한다.
5. 음향 효과를 청력 손실, 위험 음악, 차량 음향, 낮은 체력 음향으로 나눈다.
6. `map.emissions`를 필드 방출과 `mon_info_update()`로 나눈다.
7. `map.items`를 차량 아이템과 지상 활성 아이템으로 나눈다.
8. 작업자 CPU 사이클을 계산 그룹별로 기록한다.

## 17. 검증 방법과 실패 조건

### 17.1 기능 검증

아래 조건을 모두 만족하면 기능 검증을 통과한다.

- 작업자 수 1, 2, 4의 상태 검증값이 같다.
- 평가 작업 제출 순서를 바꿔도 상태 검증값이 같다.
- 같은 대상의 변경 레코드는 순서 키대로 적용된다.
- 소유 결과 위치마다 작성자가 하나다.
- 평가 작업 중 `turn_input_state`가 바뀌지 않는다.
- 게임 종료 뒤 작업자 스레드가 남지 않는다.
- 오디오 라이브러리는 오디오 소유 스레드만 호출한다.

조건 하나가 실패하면 병렬 실행 모드를 기본값으로 설정하지 않는다.

### 17.2 성능 검증

성능 비교는 새 코드의 직렬 실행 모드와 병렬 실행 모드 사이에서 수행한다. 과거 프로파일 파일 하나만으로 속도 향상을 판정하지 않는다.

각 실행 모드는 같은 난수 초기값으로 10,000턴을 세 번 실행한다. 세 실행의 중앙값을 사용한다.

`경과 시간`은 턴 시작부터 턴 종료까지 벽시계로 잰 실제 시간이다. 프로파일 JSON은 경과 시간을 `elapsed_microseconds`로 기록한다.

성능 보고서는 아래 값을 포함한다.

```text
턴 평균 경과 시간
턴 경과 시간 중앙값
턴 경과 시간 99백분위 값
프로세스 CPU 사이클
주 스레드 CPU 사이클
계산 그룹별 작업자 CPU 사이클
계산 그룹별 병합기 CPU 사이클
턴당 변경 레코드 수
턴당 같은 대상 충돌 수
```

병렬 실행 모드의 턴 평균 경과 시간이 직렬 실행 모드보다 작아야 한다. 병렬 실행 모드의 99백분위 경과 시간도 작아야 한다.

두 조건 중 하나가 실패하면 작업 크기와 병합 비용을 다시 측정한다. 두 조건을 통과하기 전에는 병렬 실행 모드를 기본값으로 설정하지 않는다.

### 17.3 전체 테스트와 프로파일 명령

전체 단위 테스트는 작업 루트에서 아래 명령으로 실행한다.

```powershell
& 'C:\cdda\test-game.ps1'
```

기준 프로파일은 작업 루트에서 아래 명령으로 실행한다.

```powershell
pwsh -File 'C:\cdda\cataclysm-dda\tools\profile-turns.ps1' `
    -Turns 10000 `
    -Seed 'cdda-turn-profile-v1' `
    -NoOpen
```

`tools/profile-turns.ps1`의 `-TurnWorkers 1`은 직렬 실행 모드를 선택한다. `-TurnWorkers 0`은 자동 작업자 수를 선택한다.

최종 직렬 프로파일은 아래 명령으로 세 번 실행한다.

```powershell
1..3 | ForEach-Object {
    pwsh -File 'C:\cdda\cataclysm-dda\tools\profile-turns.ps1' `
        -Turns 10000 `
        -Seed 'cdda-turn-profile-v1' `
        -TurnWorkers 1 `
        -OutputDirectory "C:\cdda\cataclysm-dda\turn-profile-results\turn-parallel-final-serial-$_" `
        -NoOpen
}
```

최종 병렬 프로파일은 아래 명령으로 세 번 실행한다.

```powershell
1..3 | ForEach-Object {
    pwsh -File 'C:\cdda\cataclysm-dda\tools\profile-turns.ps1' `
        -Turns 10000 `
        -Seed 'cdda-turn-profile-v1' `
        -TurnWorkers 0 `
        -OutputDirectory "C:\cdda\cataclysm-dda\turn-profile-results\turn-parallel-final-parallel-$_" `
        -NoOpen
}
```

여섯 출력 디렉터리 중 하나가 이미 존재하면 프로파일 실행을 시작하지 않는다. 존재하는 경로를 사용자에게 보고한다.

개발 중 짧은 확인은 500턴을 사용한다. 500턴 결과는 최종 성능 판정을 대신하지 않는다.

## 19. 금지 사항

- 기존 사용자 변경을 reset, checkout, stash로 제거하지 않는다.
- 모든 소유 결과를 변경 레코드로 만들지 않는다.
- 턴마다 작업자 스레드를 만들지 않는다.
- 평가 작업에서 전역 난수 엔진을 호출하지 않는다.
- 작업자 스레드에서 오디오 라이브러리를 호출하지 않는다.
- 포인터 주소로 적용 순서를 정하지 않는다.
- 필드와 활성 아이템이 없는 타일에 평가 작업을 만들지 않는다.
- GPU를 기능 정확성에 필요한 구성 요소로 만들지 않는다.
- 현재 직렬 엔진과 비트 단위 동일성을 완료 조건으로 만들지 않는다.

## 21. 권장 스킬

새 세션은 아래 스킬을 순서대로 사용한다.

1. `memory-harness`로 작업 기억을 읽고 갱신한다.
2. `graphify`로 호출 경로와 자료 구조 관계를 찾는다.
3. `test-driven-development`로 각 하위 절의 실패 테스트를 먼저 만든다.
4. `ponytail`로 6절과 7절에 없는 범용 구조를 추가하지 않는다.
5. `verify-rounds`로 결정성, 기능, 성능 근거를 검증한다.
6. `commit-harness`로 커밋과 기억 노드를 함께 정리한다.

`write-for-reader`는 설계 문서와 최종 성능 보고서를 작성할 때 사용한다.

## 22. 새 세션의 최종 반환 형식

새 세션은 반환의 첫 낱말로 `완료` 또는 `차단`을 쓴다.

`완료` 반환은 아래 항목을 모두 채운다.

```text
처분: 완료
변경 파일: 경로 전건
병렬 전환한 측정 요소: 13개 이름 전건
직렬 상태 검증값: 값
병렬 상태 검증값: 값
전체 테스트: 실행 명령과 결과
직렬 프로파일: 결과 디렉터리 3개
병렬 프로파일: 결과 디렉터리 3개
평균 경과 시간 비교: 두 수치와 변화율
99백분위 경과 시간 비교: 두 수치와 변화율
턴당 변경 레코드 수: 수치
턴당 같은 대상 충돌 수: 수치
남은 완료 조건: 없음
```

`차단` 반환은 아래 항목을 모두 채운다.

```text
처분: 차단
완료한 구현 절: 절 번호 전건
반복된 차단 조건: 구체적인 조건
차단을 입증한 명령: 명령과 출력 요약
사용자에게 필요한 결정: 하나의 닫힌 결정

검사하지 않은 범위: 경로 또는 절 전건
```
